# Design

## Context

Мотивация — в proposal.md («Why»). Требования — в `specs/`.

Принцип владельца: testpilot — инструмент агента-разработчика. Агент делает как можно меньше вызовов и ошибок. Всё, что можно автоматизировать, делает движок, а не агент параметрами. Отсюда правило: `ok` — только подтверждённый эффект; ожидание, повтор и диалоги — внутри действия; параметр — только для редкого исключения.

Ниже — факты о текущем коде, которые определяют подход.

- Фильтр кода есть только в Python: `app/_code_execution.py` (`DEFAULT_FORBIDDEN`, `ALWAYS_FORBIDDEN`, `validate_code`). Обработка `Testpilot.epf` слова не проверяет, она исполняет `Выполнить(Код)`.
- `click` (`app/_runtime.py`, `tc_click`) отправляет команду и при READBACK добавляет `_action_diagnostics.collect` (активное окно, сообщения). Состояния «до» и проверки нет.
- `input_text` возвращает `value_before`, `value_after`, `committed`, `input_status`. `accepted` значит «текст зафиксирован», а не «значение совпало». Тип значения поля движку неизвестен: обработка в `form_details` отдаёт `type_restriction` элемента, но не тип данных по пути к данным.
- Ответ на вопрос (`_answer_confirm_dialog`) уже распознаёт диалог по дереву окна (`Group[Buttons]`, `Decoration[Message]`) и возвращается, как только диалог найден. Без диалога ждёт весь `timeout` и отвечает `ok: true` с пустыми полями.
- `select_value` (`app/_value_selection.py`) уже выбирает с проверкой; при `unsupported_receiver` (код 17) повторов нет.
- Профили: `app/_profiles.py`, один YAML в `TC1C_PROFILES_FILE`, параметр `profile` у `connect`/`launch_client`. MCP уже работает по stdio (`TC1C_TRANSPORT=stdio`) и держит пул подключений. Правила общего порта нет, состояние запущенных клиентов живёт только в памяти процесса.
- Python API `Client(profile=...).start()` запускает клиент с `/Execute`, подтверждает предупреждение безопасности, ждёт готовности. `close()` останавливает запущенный процесс. CLI, кроме MCP-сервера, нет.
- Фикстура `testpilot` не сбрасывает клиент и знает один профиль (`--tc-profile`).
- `Testpilot.epf` лежит в `onec/Testpilot/` и в wheel не попадает.
- Ролевые пользователи кита — `data/role-access-seed.json` проекта (`users[].login`). Профили TestManager кит генерирует из него в `scripts/worktree_setup.py`, ролевые профили делят один порт (`PORT_OFFSETS["role"]`).

## Goals / Non-Goals

**Goals:**
- Один вызов действия даёт проверенный результат или ошибку с диагностикой, по которой агент чинит тест без дополнительных чтений.
- Тест независим от предыдущего: начальная страница перед тестом, нужный пользователь, данные убраны после.
- Кит ставит форк одним пакетом и одним MCP-сервером на дерево.

**Non-Goals:**
- Проверка эффекта у прочих действий (`set_check`, навигация по строкам, `set_list_settings`…) в этом изменении. Они сохраняют текущий readback; перенос принципа на них — следующее изменение.
- Откат транзакции на весь тест, моки, `ЮТест.Данные()` — остаётся в YAxUnit.
- Чтение `role-access-seed.json` движком: профили из него генерирует кит.
- Relay MCP на WS — сторона кита.
- Работа с Linux по сети — только спайк, по решению владельца (tasks.md, задача 11.3).

## Decisions

### Фильтр кода удаляется целиком
`DEFAULT_FORBIDDEN`, `ALWAYS_FORBIDDEN`, `Settings.forbidden` и чтение `TC1C_CODE_FORBIDDEN_WORDS`/`TC1C_CODE_ALLOWED_WORDS` удаляются. `validate_code` проверяет только непустую строку и незакрытый литерал.
- Отвергнуто: пустые списки по умолчанию с сохранением переменных — мёртвая настройка, иллюзия защиты.
- Отвергнуто: снять только `Выполнить` — `Записать`/`Удалить` требовали бы переменную в каждом окружении кита.

### А. Действие само подтверждает эффект
`click` выполняется циклом «снять состояние → команда → наблюдать → решить».

Состояние: ключ, url и заголовок активного окна; набор окон; модифицированность формы; значения полей формы из readback; сообщения пользователю; признак модального окна. С обработкой к этому добавляются ссылка и `Проведен` объекта формы (новый режим `object_state` в `Testpilot.epf`).

Ожидаемый эффект выводится по имени команды. Таблица в коде, по имени элемента и стандартному идентификатору команды:

| Команда | Эффект |
|---|---|
| Записать | `modified` = false и есть ссылка |
| Провести | `Проведен` = true |
| ЗаписатьИЗакрыть, ПровестиИЗакрыть | то же, и окно формы закрыто |
| Закрыть, ОК, Выбрать | окно формы закрыто |
| Создать | открыто новое окно формы |
| прочие | любое отличие состояния |

Решение:
- Ожидаемый эффект наблюдается — `ok: true` с `effect` и тем, что изменилось.
- Появилось сообщение об ошибке или окно ошибки — `ok: false` сразу.
- Появился модальный вопрос — переход к разделу Б.
- Иначе опрос состояния с шагом 0,2 с до половины `timeout`, затем один повтор команды, если состояние не изменилось ни в чём, затем опрос до `timeout`.

Ошибка `effect_not_observed` содержит:
- `expected`;
- активное окно и форму;
- тексты окон ошибок и сообщений;
- `snapshot` — путь к слепку формы в артефактах (pytest) или во временном каталоге (MCP).

`expect="none"` — единственный параметр-исключение: команда принята — `ok: true`.

Без обработки `Проведен` не наблюдается: `Провести` возвращает `code: effect_unverifiable` с подсказкой подключить обработку. Обработка идёт в пакете и запускается по умолчанию (Г), так что для кита это не обычный путь.

- Отвергнуто: эффект в ответе и проверка по `expect` (прежнее А1). Это противоречит принципу: обычная проверка ложится на агента параметрами.
- Отвергнуто: повтор без условия. Повтор `Создать` при медленном сервере открыл бы две формы. Поэтому повтор один и только при полностью неизменном состоянии.
- Цена: опрос на каждом клике. Успешный клик стоит одно чтение «до» и одно-два «после»; ожидание есть только там, где эффекта ещё нет.

### Б. Диалоги обрабатывает движок
Модальный вопрос распознаётся тем же разбором дерева, что в `_answer_confirm_dialog`, расширенным до заголовков всех кнопок; окно ошибки 1С распознаётся как диалог с одной кнопкой «ОК» и текстом ошибки.
- `click(answer="Да")` нажимает кнопку с этим заголовком (точное совпадение без учёта регистра) и продолжает проверку эффекта действия. Ответ содержит `dialog: {question, buttons, answered}`.
- Без `answer` диалог даёт `ok: false`, `code: unexpected_dialog` сразу, с текстом и кнопками.
- `answer` задан, а диалога не было — `ok: true`, `dialog: null`. Подтверждение бывает условным, например вопрос только при изменениях; если такой вызов падал, агент писал бы ветвление.
- `answer_dialog(confirm|answer, timeout=5)` возвращается сразу после нажатия. Нет диалога весь `timeout` — `ok: false`, `code: no_dialog`; сейчас в этом случае `ok: true`.
- Отвергнуто (прежнее Б1): `wait=0` по умолчанию — ожидание перекладывалось на агента параметром.
- Отвергнуто: строгая ошибка при `answer` без диалога — лишние ошибки на условных подтверждениях.

### input_text: сравнение по типу поля, ссылочные поля через выбор
Тип значения берёт обработка: новый признак `value_type` в `form_details` по пути к данным элемента. Это `Число`, `Дата`, `Булево`, `Строка` или имя ссылочного типа. Дальше:
- **Число** — оба текста разбираются по разделителям сеанса (обработка уже отдаёт `separators`), сравниваются числа: «2» = «2,000», «2» ≠ «20».
- **Дата** — разбор по формату сеанса; введённая дата без времени равна дате с нулевым временем.
- **Булево** — по значению («Да»/«Нет», «Истина»/«Ложь»).
- **Строка** — точное равенство.
- **Ссылочный тип** — ввод идёт через выбор `select_value` с `value=text` и точным совпадением представления. Ноль или несколько совпадений — `ok: false` (`value_not_found` или `ambiguous_value`) и `candidates`.

Без обработки тип неизвестен, и сравнение — точное равенство строк. Начало строки не используется никогда.
- Отвергнуто: «равные числа или префикс» (прежнее правило). Пропускает «Протон» → «Протон-2».
- Отвергнуто: угадывать тип по тексту. «2,000» в строковом поле тогда равнялось бы «2».
- Цена: доработка обработки (`value_type`, `object_state`) и её пересборка Конфигуратором на Windows. Протокол обработки — версия 2; Python принимает 1 и 2, а без новых режимов работает как без обработки.

### select_value: повтор шага при `unsupported_receiver`
Шаг выбора пункта оборачивается циклом. При статусе 17 значение поля перечитывается. Если оно не изменилось — 0,2 с, список читается заново, шаг повторяется; если изменилось — обычная проверка `expected`. Предел — `timeout`. В ответе добавляется `attempts`.
- Отвергнуто: повтор всего `select_value` снаружи — двойное открытие формы выбора и риск двойного выбора.

### Client.reset() и фикстура
`Client.reset()` — перенос `close_all` из спайка в клиент. Вопрос о сохранении обрабатывается механизмом Б (`close(answer="Нет")`), поэтому таймаут не ждётся. В цикле: отменить редактирование строк → закрыть окно с `answer="Нет"` → повторять, пока активна не начальная страница (не больше 10 окон). Фикстура вызывает `reset()` перед каждым тестом.
- Отвергнуто: опция отключения сброса — нет потребителя.

### Ролевые клиенты и общий порт
Профили — обычные записи YAML. Кит генерирует их из `role-access-seed.json`: `ib`, `daily`, `роль:<логин>` с общим `port`.

Правило порта применяется в одном месте запуска (`launch_client`), поэтому одинаково работает для MCP, CLI и pytest:
- Перед запуском читается файл состояния `.testpilot-clients.json` рядом с файлом профилей: `{"<host>:<port>": {profile, pid, started}}`. Запись атомарная, через временный файл и переименование.
- Если на порту живой клиент того же профиля — подключение без запуска.
- Если клиент другого профиля, запущенный testpilot, — он останавливается. Сначала проверяется, что это действительно тот процесс: имя `1cv8*` и `-TPort <port>` в командной строке, иначе pid мог быть переиспользован.
- Порт слушает процесс без записи — `port_busy` с pid.

Пользователь теста — маркер `@pytest.mark.testpilot(user="kfk_user")` или `@pytest.mark.testpilot(profile="…")`; для параметризации — то же через `indirect` фикстуры `testpilot_user`. Профиль ищется среди профилей файла с `user` = логин и тем же `base`/`server`, что у `--tc-profile`. Ровно одно совпадение, иначе ошибка setup со списком. Сессия фикстуры помнит текущий профиль. При смене пользователя она закрывает клиент и запускает новый, при том же пользователе делает `reset()`.

MCP: один stdio-сервер на дерево со всем файлом профилей, профиль — параметр `connect`/`launch_client` (уже есть). Новое — только правило порта и файл состояния.

- Отвергнуто: testpilot сам читает `role-access-seed.json`. Формат кита попал бы в общий движок, и профили разошлись бы с теми, что видит кит.
- Отвергнуто: состояние только в памяти процесса. CLI `client start` и последующий pytest — разные процессы, без файла pytest не знает, кто на порту.
- Отвергнуто: отдельный порт на каждую роль. Противоречит раскладке портов кита (10 портов на дерево).

### В1. testpilot_data: физическое удаление в режиме загрузки
Фикстура хранит ссылки в порядке учёта:
- `create(code, parameters)` учитывает все ссылки из `Результат`, рекурсивно;
- `track(ref)` — ссылку от теста;
- `track_window()` — ссылку активного окна: с обработкой из `object_state`, без неё из `ref=` в url.

Teardown одним серверным вызовом, в обратном порядке, для каждого объекта:
1. Объекта нет — пропустить.
2. `ОбменДанными.Загрузка = Истина`.
3. Проведённый документ записать в режиме `ОтменаПроведения`.
4. `Удалить()`.

Ошибки собираются, затем teardown падает со списком.
- Отвергнуто (В2): `Удалить()` без загрузки — подписки и ссылочная целостность мешают удалять в любом порядке.
- Отвергнуто (В3): пометка удаления — данные копятся и мешают выбору по строке.

### CLI `1c-testpilot client start|stop`
Подкоманда в `app/_cli.py` поверх Python API и того же правила порта. `start` запускает клиент, пишет состояние, делает `disconnect` вместо `close` и печатает JSON. Процесс стартует отвязанным (`DETACHED_PROCESS`/`start_new_session`). `stop` работает по `--pid` или `--profile`, с той же проверкой процесса. Без подкоманды `1c-testpilot` запускает MCP-сервер, как раньше.
- Отвергнуто: скрипт запуска в ките — подтверждение предупреждения и проверка протокола обработки жили бы в двух местах.
- Отвергнуто: держать CLI, пока жив клиент — pytest не подключится, пока CLI держит соединение.

### Г1. Testpilot.epf в пакете
Бинарник переносится в `app/testpilot_assets/` (`package-data`), путь по умолчанию — через `importlib.resources`. `build.py` пишет туда же.
- Отвергнуто (Г2): файл в `onec/` — кит держал бы клон ради одного файла.
- Отвергнуто: `data-files` setuptools — устарело, путь зависит от окружения.

## Risks / Trade-offs

- [Повтор клика выполнит действие дважды, если эффект пришёл позже половины таймаута и не изменил состояние] → повтор только при полностью неизменном состоянии, один раз; в ответе `repeated: true`.
- [Таблица стандартных команд не покрывает команды конфигурации с другими именами] → для них действует «любое изменение»; таблица пополняется по фактам живых прогонов.
- [Изменения обработки требуют пересборки на Windows и Конфигуратора] → сборка — задача на WS по согласованию; Python совместим с протоколом 1.
- [Тест-клиент принимает одно соединение: если `start` не отключился, pytest не подключится] → `start` отключается явно, проверка — в интеграционной задаче.
- [Файл состояния устарел (клиент убит вручную)] → запись с мёртвым pid или чужой командной строкой игнорируется.
- [Снят фильтр — любой код под пользователем клиента] → код выключен по умолчанию; в README: защита — права 1С и отдельная dev-ИБ.
- [Перенос epf конфликтует со слиянием апстрима] → пункт чек-листа синхронизации.
- [Удаление в режиме загрузки обходит бизнес-логику; `ОтменаПроведения` при загрузке не проверена на нашей конфигурации] → живой прогон в dev-ИБ по согласованию; до него задача не закрыта.

## Migration Plan

1. Слить PR в `fork` после ок владельца и выпустить тег `v1.9.2.post3`.
2. Кит переходит на тег. Он генерирует профили `ib`, `daily`, `роль:<логин>` и удаляет переменные `TC1C_CODE_*_WORDS`.
3. Изменения поведения для существующих MCP-агентов: `click` может вернуть `ok: false` там, где раньше был `ok: true`; `answer_dialog` без диалога — `ok: false`. Обе правки описаны в документации инструментов.
4. Откат — коммит `04c5531` ветки `fork` (1.9.2.post2, тега нет) или тег `v1.9.2`. Данные и схема ИБ не меняются.
