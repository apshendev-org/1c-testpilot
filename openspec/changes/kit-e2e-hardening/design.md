# Design

## Context

Мотивация — в proposal.md («Why»). Требования — в `specs/`. Ниже — факты о текущем коде, которые определяют подход.

- Фильтр кода есть только в Python: `app/_code_execution.py` (`DEFAULT_FORBIDDEN`, `ALWAYS_FORBIDDEN`, `validate_code`). Обработка `onec/Testpilot/src/.../Helper/Ext/Form/Module.bsl` слова не проверяет, она исполняет `Выполнить(Код)` в `&НаСервере`/`&НаКлиенте`. Поэтому пересборка epf не нужна.
- `click` (`app/_runtime.py`, `tc_click`) отправляет команду и при READBACK добавляет `_action_diagnostics.collect` (активное окно, сообщения). Состояния «до» нет, сравнения нет.
- `input_text` уже возвращает `value_before`, `value_after`, `changed`, `committed`, `input_status`. Но `accepted` означает «текст зафиксирован», а не «значение совпало с введённым». Этот случай спайк и поймал на группе номенклатуры.
- `select_value` (`app/_value_selection.py`, `run`) при исключении возвращает `selection_sent` и `stage`, повторов нет. `unsupported_receiver` — код 17 в `app/tc1c.py`.
- `answer_dialog`: `timeout` (по умолчанию 5) — это и есть время ожидания. Без диалога цикл `_answer_confirm_dialog` крутится до конца с шагом 0,3 с.
- Фикстура `testpilot` (`app/testpilot_pytest.py`) не сбрасывает состояние клиента. Спайк писал свой `close_all`.
- Запуск без MCP уже есть в Python API: `Client(profile=...).start()` делает `launch_client` с `/Execute`, подтверждает предупреждение и ждёт готовности. Но `close()` останавливает запущенный процесс, а у `1c-testpilot` нет подкоманд, только MCP-сервер.
- `Testpilot.epf` лежит в `onec/Testpilot/`, а пакет собирается из `app/` (`package-dir`), поэтому в wheel обработка не попадает.

## Goals / Non-Goals

**Goals:**
- Агент получает из ответа действия достаточно данных, чтобы утверждать результат без отдельного чтения формы.
- Тест независим от предыдущего: начальная страница перед тестом, данные убраны после.
- Кит ставит форк одним пакетом, без клона репозитория.

**Non-Goals:**
- Откат транзакции на весь тест, моки, `ЮТест.Данные()` — это остаётся в YAxUnit.
- Изменение протокола или модуля обработки Testpilot.
- Работа с Linux по сети: только отдельный спайк, по решению владельца (tasks.md, задача 9.3).

## Decisions

### Фильтр кода удаляется целиком
`DEFAULT_FORBIDDEN`, `ALWAYS_FORBIDDEN`, поле `Settings.forbidden` и чтение `TC1C_CODE_FORBIDDEN_WORDS`/`TC1C_CODE_ALLOWED_WORDS` удаляются. `validate_code` проверяет только непустую строку и незакрытый литерал (токенизатор остаётся, он нужен и для запросов).
- Отвергнуто: оставить пустые списки по умолчанию и переменные. Это мёртвая настройка, которая создаёт иллюзию защиты.
- Отвергнуто: снять только `Выполнить`. Запрос в коде заработал бы, но `Записать`/`Удалить` всё равно требовали бы переменную в каждом окружении кита.
- Защита — `TC1C_CODE_EXECUTION=false` по умолчанию и права пользователя 1С. Это пишем в README.

### А1. click: эффект в ответе, ошибка только по `expect`
Перед командой читается лёгкое состояние: ключ и url активного окна, `current_modified` формы-владельца, число окон. После команды — то же самое; ответ получает `before`, `after`, `changed`. `expect` проверяет так:
- `changed` — любое отличие;
- `saved` — у формы-владельца `modified` стало `false`, а url содержит `ref=`;
- `closed` — окна-владельца больше нет;
- `window` — активным стало другое окно.

Не выполнено — `ok: false`, `code: effect_not_observed`, к ответу добавляются сообщения пользователю из диагностики.
- Отвергнуто (А2): падать при `changed: false` всегда. Ломает клики по декорациям, гиперссылкам и командам без видимого эффекта, а также существующие сценарии MCP-агентов.
- Цена: 2–3 лишних чтения на клик (по замерам спайка чтение — десятки мс). При `TC1C_READBACK=false` состояния не читаются, `expect` тогда возвращает `invalid_argument`.

### input_text: сверка итогового представления
Используется существующий `value_after`. Совпадение: оба текста — числа (пробелы и неразрывные пробелы убираются, запятая считается десятичным разделителем), и числа равны; иначе `value_after.startswith(text)`. Префикс покрывает «Ромашка ОАО (ДМ-000002)» и даты с временем. Подмена группой даёт `value_mismatch`. Если `committed` не `true` или `value_after` не прочитан, то `verified: null`, а поведение прежнее (`pending`/`unverified`).
- Отвергнуто: точное равенство строк. Ложные падения на «2» → «2,000».
- Отвергнуто: сверка через данные (тип и ссылка). Нужна обработка, а `input_text` работает и без неё.

### select_value: повтор шага при `unsupported_receiver`
В `Selector` шаг выбора пункта (выпадающий список или форма выбора) оборачивается циклом. При `OperationError` со статусом 17 система перечитывает значение поля. Если оно не изменилось, ждёт 0,2 с, заново получает список и повторяет; если изменилось, выходит в обычную `verify`. Предел — общий `deadline` вызова (`timeout`). В ответ добавляется `attempts`.
- Отвергнуто: повтор всего `select_value` снаружи. Повторное открытие формы выбора и двойной выбор, если первый всё-таки прошёл.

### Б1. answer_dialog: сразу, ждать только явно
Новый параметр `wait` (по умолчанию 0). `timeout` остаётся псевдонимом `wait` для старых вызовов, но его значение по умолчанию становится 0. При 0 делается один обход окна: вопроса нет — `code: no_dialog`.
- Отвергнуто (Б2): короткое ожидание по умолчанию (0,5 с). Каждый вызов без диалога всё равно платит время, а «диалог появится через 0,6 с» ломается так же.
- Изменение поведения: вызовы без аргументов раньше ждали 5 с. Описание инструмента MCP подсказывает агенту `wait` после действий, открывающих вопрос.

### Client.reset() и фикстура
`Client.reset(max_windows=10)` — перенос `close_all` из спайка внутрь клиента, без ожиданий по таймауту. В цикле:
1. Отменить редактирование строк таблиц активной формы.
2. Закрыть окно.
3. Если активным стало окно вопроса, ответить «Нет» (`answer_dialog(confirm=False)` с `wait=0`).
4. Повторять, пока активна не начальная страница.

Фикстура `testpilot` вызывает `reset()` после `prepare` при любой области жизни клиента; ошибка проваливает setup.
- Отвергнуто: опция `--tc-reset none`. Не нужна, пока нет потребителя, которому мешает сброс.

### В1. testpilot_data: физическое удаление в режиме загрузки
Фикстура хранит список ссылок в порядке учёта.
- `create(code, parameters)` исполняет серверный код и учитывает все ссылки из `Результат`: ссылку, структуру или массив, рекурсивно.
- `track(ref)` учитывает ссылку, переданную тестом.
- `track_window()` берёт `ref=` из url активного окна и вид объекта из пути и восстанавливает ссылку серверным кодом по GUID. Порядок байт GUID в url — проверить юнит-тестом на образце из спайка и живым прогоном.

В teardown учтённые объекты удаляются одним серверным вызовом, в обратном порядке. Для каждого объекта:
1. Получить объект; если его нет, пропустить.
2. Установить `ОбменДанными.Загрузка = Истина`.
3. Документ с `Проведен = Истина` сначала записать в режиме `ОтменаПроведения`.
4. `Удалить()`.

Ошибки собираются по каждому объекту, затем teardown падает со списком.
- Отвергнуто (В2): `Удалить()` без загрузки. Подписки и проверки ссылочной целостности конфигурации мешают удалять связанные тестовые данные в любом порядке.
- Отвергнуто (В3): пометка удаления. Данные копятся в dev-ИБ и мешают выбору по строке в следующих тестах.
- Как в YAxUnit (`УдалениеТестовыхДанных`): физическое удаление, обратный порядок.

### CLI `1c-testpilot client start|stop`
Подкоманда в `app/_cli.py` поверх Python API. `start` вызывает `Client(profile=...).start()`, затем `disconnect` вместо `close`, чтобы процесс остался жить; печатает JSON. Процесс уже стартует отвязанным (`DETACHED_PROCESS`/`start_new_session`), поэтому переживает выход команды. `stop` завершает процесс по pid (`psutil`) или находит его по порту профиля; чужие процессы 1С без этого порта не трогает. Без подкоманды `1c-testpilot` по-прежнему запускает MCP-сервер.
- Отвергнуто: отдельный скрипт кита, который повторяет запуск. Тогда подтверждение предупреждения безопасности и проверка версии протокола обработки живут в двух местах.
- Отвергнуто: держать процесс CLI, пока клиент работает. dev_ib.py тогда сам управляет фоновым процессом, а pytest не может подключиться, пока CLI держит соединение.

### Г1. Testpilot.epf в пакете
Бинарник переносится в пакет `app/testpilot_assets/` (`__init__.py`, `Testpilot.epf`, `package-data`). По умолчанию путь берётся через `importlib.resources`, если `code_epf` и `TC1C_CODE_EPF` не заданы. `onec/Testpilot/build.py` по умолчанию пишет туда же. Ссылки в README и `profiles.example.yaml` обновляются.
- Отвергнуто (Г2): оставить файл в `onec/`. Тогда кит держит клон форка ради одного файла и следит, чтобы версия клона совпадала с пакетом.
- Отвергнуто: `data-files` setuptools. Устарело, путь установки зависит от окружения.

## Risks / Trade-offs

- [Тест-клиент принимает одно соединение: если `start` не отключился, pytest не подключится] → `start` отключается явно и только потом выходит; это проверяется в интеграционной задаче.

- [Снят фильтр — агент может выполнить любой код под пользователем клиента] → по умолчанию код выключен; в README прямо сказано, что защита — права пользователя 1С и отдельная dev-ИБ.
- [Перенос epf конфликтует при слиянии апстрима, который меняет `onec/Testpilot/Testpilot.epf`] → git распознаёт переименование; при обновлении апстрима переносим файл заново, это пункт чек-листа синхронизации в tasks.
- [Префиксное сравнение `input_text` пропустит «Протон» → «Протон-2»] → для точного выбора остаётся `select_value` с `expected`; это указано в описании действия.
- [Удаление в режиме загрузки обходит бизнес-логику, могут остаться записи независимых регистров] → фикстура удаляет только учтённые объекты; это граница ответственности, она описана в документации.
- [`ОтменаПроведения` при `Загрузка = Истина` и поведение движений не проверены на нашей конфигурации] → живой прогон в dev-ИБ по согласованию; до него задача не закрывается.
- [`click` с чтением «до» замедляет шаг] → чтения короткие; при `TC1C_READBACK=false` их нет.
